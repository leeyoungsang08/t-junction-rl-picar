# 가상 실차 6대로 하는 Real-to-Sim / Sim-to-Real 예행연습 (2026-11-11)

실물 PiCar를 당장 쓸 수 없어서, **실차가 있다고 가정하고** 실차에 올리기 전에 필요한 전 과정을 시뮬레이션에서 끝까지 해 본 기록이다.
핵심은 "가상 실차"다. 6대가 저마다 다른 하드웨어(모터 좌우 차, 카메라 장착 오차, 센서 잡음, 통신 손실)를 갖고, 주행 코드는 그 값을 모른다.
주행 코드가 아는 것은 사람이 실차에서 줄자·각도기·사진 한 장으로 잴 수 있는 것뿐이다. 그래서 여기서 통과한 절차와 파일 형식을 실차에 그대로 쓴다.

**모든 하드웨어 범위는 가정이다.** 실차를 재면 `picar_gazebo/picar_gazebo/virtual_fleet.py`의 `PRIORS`를 실측 범위로 바꾸고 같은 명령을 다시 돌린다.

## 1. 전체 흐름

```text
[가상 실차 6대: 숨은 참값]  fleet_truth.yaml
        │  ① 차마다 측정 (줄자·각도기 오차 포함)          rehearsal measure
        ▼
[차별 보정 파일]  calib/car0.yaml … car5.yaml   ← 실차에서도 같은 파일
        │  ② 6대 동시 주행 (실제 주행 코드 + 실제 중앙 서버)   rehearsal drive  /  Gazebo FLEET=…
        ▼
[주행 기록]  정지 오차, 교차로 통과 시간, 순항 속도 …   field_measurements.csv
        │  ③ SUMO 보정 (속도·가감속·교차로 통과 시간·랜덤화 범위)   picar_sim.calibrate
        ▼
[보정된 SUMO]  course_fleet.yaml (+ 전용 맵)
        │  ④ 기존 정책 평가 → 필요하면 측정 범위 랜덤화로 재학습   picar_sim.train --randomize
        ▼
[정책]  ⑤ 가상 실차 6대에서 규칙 대 DQN 비교 (Sim-to-Real 확인)
```

## 2. 가상 실차: 무엇을 얼마나 다르게 가정했나

차마다 아래 범위에서 뽑는다(`sample_fleet(6, seed)`). 근거는 이 급의 차(저가 DC 기어 모터, 출력물 브래킷에 단 Pi 카메라, IR 라인 센서, HC-SR04, Wi-Fi UDP)의 일반적인 수준이다.

| 항목 | 가정 범위 | 왜 |
|---|---|---|
| 좌·우 모터 세기 | 각각 평균 1.00, 표준편차 4% (0.88~1.10) | 같은 PWM에서 저가 기어 모터 속도는 몇 %씩 다르다 → 직진 때 한쪽으로 휨 |
| 배터리 | 시작 0.92~1.02배, 분당 0~0.4% 감소 | 충전 상태에 따라 전체 속도가 달라지고 달리면서 떨어짐 |
| 데드밴드 | 바퀴 속도 0.02~0.05 m/s 아래는 안 돎 | 약한 명령에는 모터가 안 움직임 |
| 명령 지연 | 0.05~0.12 s | ROS + PWM + 모터 시정수 |
| 가속 한계 | 0.7~1.3 m/s², 5~10 rad/s² | |
| 제자리 회전 효율 | 명령의 0.82~0.97배, 회전마다 ±1~3% 흔들림, 0~8% 확률로 한 번 더 −8% | 타이어가 끌리고 바퀴가 가끔 늦게 출발 |
| 속도 잔떨림 | 1~3% | 바닥·기어 |
| 카메라 장착 | 상하 ±1.5°, 좌우 ±1.5°(1σ, 최대 3°), 옆 ±4 mm, 높이 ±3 mm | 브래킷 조립 오차 |
| 카메라 영상 | 잡음 1~4%, 밝기 0.8~1.15배, 지연 30~90 ms, 프레임 손실 0~5% | |
| IR | 채널당 0~1% 오검출 | |
| 초음파 | 오차 0.5~1.5 cm, 0~5% 무응답 | |
| UDP | 손실 0~5%, 지연 5~40 ms | |

사람이 재는 오차도 넣었다: 줄자 ±2 mm, 각도기 ±1.5°, 차를 눈대중으로 세울 때 옆 ±3 mm·방향 ±0.7°, 항목마다 3번 반복.

## 3. 차마다 재는 것 (실차에서도 똑같이)

| 시험 | 방법 | 나오는 값 |
|---|---|---|
| 직진 1 m | 0.2 m/s로 5초 명령 후 간 거리와 틀어진 각도 | `speed_scale`(실제 간 거리/명령 거리), `trim_per_m`(좌우 차 보정) |
| 정지 굴러감 | 0.15, 0.25 m/s에서 정지 명령 후 더 간 거리 | `latency_s`, `accel_mps2` |
| 제자리 90° 회전 | 45°/s로 좌 3번·우 3번, 실제 돈 각도 | `turn_scale`, 회전 흔들림(표준편차) |
| 카메라 사진 3장 | 직선 차로 한가운데에 똑바로 세우고 촬영 | `cam_pitch_deg`, `cam_yaw_deg`, `cam_y_m` |

실차 명령:

```bash
python3 -m picar_lab.car_agent.calibration --out car0.yaml --straight-m 0.95 --drift-deg -8 \
    --roll-slow-m 0.020 --roll-fast-m 0.045 --spin-deg 84,86,85,83,85,84
python3 -m picar_lab.car_agent.camera_calib --image frame.png --lane-width 0.21 --out car0.yaml
```

카메라 보정 정확도(가상 실차 6대): 좌우 각도 오차 평균 0.4°, 옆 위치 오차 1~3 mm. 남는 오차는 거의 차를 세울 때의 눈대중 오차다.

## 4. 실행 방법

```bash
# 2D (ROS·Gazebo 불필요, 6대 5분 주행이 1~2분)
python3 -m picar_gazebo.rehearsal fleet   --out runs/my_fleet --cars 6 --seed 7     # 숨은 참값
python3 -m picar_gazebo.rehearsal measure --out runs/my_fleet                       # 차별 보정 파일
python3 -m picar_gazebo.rehearsal drive   --out runs/my_fleet --calib full --seconds 300 --seed 1
python3 -m picar_gazebo.rehearsal ladder  --out runs/my_fleet       # 보정 없음 → 공용 → 모터 → 모터+카메라 비교

# Gazebo (PC): 같은 6대를 차마다 보정한 뒤 합격 실행
CARS=6 FLEET=runs/rehearsal_v1/fleet_truth.yaml MINUTES=5 SEEDS="1" CONTROLLERS="rule dqn" \
    bash picar_gazebo/scripts/run_acceptance.sh

# SUMO 보정과 재학습
python3 -m picar_sim.calibrate --csv runs/rehearsal_v1/field_measurements.csv --out runs/rehearsal_v1/course_fleet.yaml
PICAR_COURSE_CONFIG=runs/rehearsal_v1/course_fleet.yaml python3 -m picar_sim.train --seed 42 --episodes 1500 \
    --out runs/picar_v10_fleet --randomize
```

`PICAR_COURSE_CONFIG`를 주면 그 설정과 전용 SUMO 맵(`<이름>_maps/`)을 쓴다. 안 주면 기존 `course.yaml` 그대로다.

수정은 seed 7 차량으로 했으므로, 다른 차량 묶음 3개(seed 11, 23, 31)로 확인했다. 6회 실행 모두 교착 0, FAULT 0, 차로 이탈 0, 통과 15.8~16.6대/분. 남은 것은 옆 스침 0~1회/5분뿐이다.

### 5.3 남은 옆 스침은 차로 폭 문제

| 차로 폭 | 6회 × 300 s의 충돌 합계 |
|---|---|
| 0.21 m (사진 추정값) | 8회 실행에 6건 |
| 0.23 m | **0건** |
| 0.25 m | **0건** |

차 폭 0.17 m에 차로 0.21 m면 마주 오는 두 차 사이가 4 cm이고, 안쪽 차로 모서리(반경 0.245 m)에서는 차 앞 모서리가 중앙선까지 닿는다.
가상 실차의 차로 추종 오차가 ±1~2 cm라서 가끔 스친다. **실물 차로 폭과 차 폭을 재는 것이 1순위**다. 2 cm만 넓어도 사라진다.

### 5.5 SUMO 보정 (Real-to-Sim의 교통 쪽)

가상 실차 주행 기록 906행에서 보정했다. 교차로 통과 시간(정지선 → 출구 센서):

| 움직임 | 가상 실차 | 보정 전 SUMO | 보정 후 SUMO | 오차 |
|---|---|---|---|---|
| 직진 | 4.33 s | 4.6 s | 4.6 s | 6% |
| 좌회전 | 7.90 s | 4.9 s (−38%) | 7.7 s | 3% |
| 우회전 | 5.54 s | 3.5 s (−37%) | 5.7 s | 3% |

PiCar는 교차로 안에서 멈춰서 제자리 회전을 하는데 SUMO 차는 그냥 쓸고 지나가서, 회전이 실제보다 37~38% 빨랐다.
움직임별 교차로 안 속도(`vehicle.turn_speed_mps`)를 맞춰서 세 움직임 모두 10% 안으로 들어왔다.
순항 속도는 0.25 → 0.241 m/s, 랜덤화 범위(속도·가감속·출발 지연·명령 지연)는 측정값의 5~95% 구간으로 바꿨다.

### 5.6 정책: 기존 것으로 되는가, 재학습이 필요한가

**보정된 SUMO에서** (test 시나리오 3개 × 시드 10개, `runs/rehearsal_v1/eval_v9_on_fleet_sumo/`, `runs/picar_v10_fleet/eval10/`):

|---|---:|---:|---:|---:|
| 기존 DQN v9 seed42 (보정 전 SUMO에서 학습) | **3.28** | **3.24** | 17.8 | 8.19 |
| 기존 DQN v9 seed43 / seed44 | 3.30 / 3.67 | 3.53 / 3.95 | 15.0 / 17.2 | 8.19 / 8.12 |
| 오래된 요청 우선 | 3.61 | 3.82 | **13.8** | 8.15 |
| 재학습 DQN v10 seed42 / seed43 (보정된 SUMO + 측정 범위 랜덤화, 1,500 에피소드) | 4.51 / 4.16 | 3.95 / 3.98 | 19.9 / 19.6 | 7.94 / 8.03 |
| 대기열 규칙 | 6.62 | 5.68 | 20.8 | 7.56 |
| 고정식 5 s | 8.12 | 7.80 | 21.5 | 7.28 |

- 충돌·교착·정지선 위반은 모두 0.
- **기존 정책(v9 seed42)은 보정 후에도 그대로 통한다.** 회전 시간이 60% 늘어난 SUMO에서도 오래된 요청 우선보다 평균 지연이 9~15% 짧다(최장 대기는 4 s 길다).
- **재학습(v10)은 이번에는 더 나빴다.** 같은 1,500 에피소드에서 랜덤화까지 넣자 규칙보다 15~25% 느린 정책이 나왔다(시드 2개). 그래서 기본 정책은 v9 seed42로 둔다.
  재학습이 필요해지는 경우는 실측 뒤 코스 치수나 신호 설정이 바뀔 때다(그때는 에피소드를 늘리고 시드 3개 이상으로).

|---|---:|---:|---:|---:|---|

(요청→진입에는 요청 지점에서 정지선까지 가는 약 5초가 들어 있다.)
- **Sim-to-Real 쪽 결론: SUMO에서 배운 정책이 가상 실차 6대를 문제없이 제어한다**(허가 없는 진입·교착·FAULT 0).
- 성능은 세 제어기가 오차 범위 안에서 같다(차이 0.2 s, 시드 간 흔들림 0.4 s). 이 코스·6대에서는 DQN의 이득이 측정되지 않는다 — 이전 SUMO 결론("오래된 요청 우선과 비슷")과 같은 방향이다.
- 실차 첫 운영은 오래된 요청 우선으로 하고 DQN은 shadow로 판단만 기록하는 기존 계획을 유지한다.

### 5.7 Gazebo에서 같은 6대 (2026-11-12)

같은 가상 실차 6대를 Gazebo에서 차마다 보정한 뒤 5분씩 돌렸다(`FLEET=`, 헤드리스). 보정값은 2D와 맞았다(예: car1 trim 0.603 / 0.589, turn_scale 0.80 / 0.81).

| 실행 | 바뀐 것 | 충돌 | 차로 이탈 | FAULT | 최장 교착 | 판정 |
|---|---|---|---|---|---|---|
| 017 | 처음 | 1 (dqn 26) | 7 | 있음 | 207 s | 불합격 |
| 018 | 카메라에 보이는 다른 차 처리 | 69 | 16 | 0 | 159 s | 불합격 |
| **020** | 코너 접촉 수정(아래) | **0** | **0** | **0** | **0** | 안전 항목 전부 통과 |
| **021** | 020과 같은 코드, 시드 2·3 × 규칙·DQN (4회) | **0** | **0** | **0** | **0** | 안전 항목 전부 통과 |

020·021 합쳐 7회(시드 3개 × 규칙·DQN, 빔 결함 1회) 모두 충돌 0, 이탈 0, FAULT 0, 교착 0, 허가 없는 진입 0, 정지 오차 p95 1.3~3.9 cm였다.
교차로 J 성능은 규칙 6.2대/분·평균 지연 10.1~11.5 s, DQN 6.0대/분·11.2~12.0 s로, Gazebo에서는 DQN이 규칙보다 낫지 않았다(5.6의 결론과 같다: 첫 운영은 규칙, DQN은 shadow).
판정표에 남은 FAIL은 실시간 비율뿐이다(0.72~0.75, 기준 0.9). PC가 카메라 6대를 실시간으로 못 그리는 것이고 주행 문제는 아니다. 주행 코드는 카메라 시각으로 돌기 때문에 느려져도 결과는 같다.

**017·018이 실패한 이유 두 가지** (2D 점검기가 못 보던 것):

1. **카메라에 다른 차가 보인다.** 2D는 바닥만 그렸다. 차 옆면과 바퀴가 검은 선처럼 보여서 차로를 잘못 잡고, 한 대는 교차로를 나와 180° 돌아 나갔다(017). → 2D 렌더러가 다른 차를 높이 있는 상자로 그리게 했고, 폭이 넓은 검은 덩어리는 차선 후보에서 뺀다.
2. **닿으면 끝난다.** 2D에서는 차끼리 겹쳐도 그냥 지나가서 "스침 1~3회"로만 셌다. Gazebo에서는 우상단 코너에서 두 차가 닿자 서로 맞물려 40초 넘게 같이 돌았고 길이 막혀 전체가 멈췄다(018, 019에서 카메라 화면을 저장해 확인). 코너에서 마주 오는 두 차 사이는 설계상 1.6 cm뿐인데, 바깥쪽 차가 진입하면서 14 mm 안쪽으로 파고들었다. → 2D에 "1.5 cm 이내 근접" 지표를 넣었다(`near_road`, `near_junction`). 수정 전 도로 구간 근접이 5분에 6~14회, 수정 후 0~1회다.

실행마다 카메라 화면을 남기려면 `DUMP_FRAMES=1`(초당 4장, `frames_<car>.u8/.csv`). 저장한 화면을 `LaneDetector`에 다시 넣으면 PC 없이 같은 판단이 재현된다.

## 6. 주행 코드에서 고친 것 (가상 실차가 드러낸 문제)

이상적인 차 3대에서는 안 보이던 문제들이다. 전부 `picar_lab/car_agent/`(실차와 공유하는 코드)에 들어갔다.

| 증상 | 원인 | 수정 |
|---|---|---|
| 차가 차로 한쪽으로 2~3 cm 치우쳐 달림 | 차선 추종에 적분이 없어 모터 좌우 차를 못 지움 | 보정한 `trim`을 미리 더하고 작은 적분 항 추가(정지 중에는 적분 안 함) |
| 교차로에서 4~8 cm 일찍/늦게 회전 | 배터리·모터 세기에 따라 실제 속도가 명령과 다른데 거리를 명령 속도로 셈 | `speed_scale` 측정 → 명령을 그만큼 올림 |
| 회전 뒤 반대 차로로 들어가 역주행 | 회전 중 "지난 프레임의 그 선" 추적이 중앙선을 오른쪽 선 자리에 끌고 옴 | 회전 중에는 추적을 끄고 좌우 위치로만 판단, 비스듬한 선은 차 옆을 지나는 위치로 판단 |
| 교차로를 20° 넘게 틀어진 채 나감 | 차로를 못 찾으면 훑다가 처음 보인 각도에서 끝냄 | 카메라로 차로 방향을 보며 10° 안으로 맞춘 뒤에만 끝냄 |
| 교차로 안에서 멈춰 전체 교착 | 반대 차로 정지선의 차가 초음파(±15°)에 20 cm로 잡힘 | 교차로를 빠져나가는 동안은 9 cm 안의 진짜 장애물에만 정지 |
| 도로 한가운데서 갑자기 회전 | 차선 위를 달리다 IR 잡음 한 번에 "정지선"으로 오인 | 4채널 모두 또는 2회 연속일 때만 정지선, 지도상 정지선까지 거리의 60% 전에는 무시 |
| 제자리에서 영영 안 움직임 | 약한 회전 명령이 모터 데드밴드 아래 | 제자리 회전은 0.7 rad/s 이상으로만 |
| 먼 쪽 끝선을 내 왼쪽 선으로 착각 | 오른쪽 선을 시야 가장자리에서 버림 | 오른쪽 선은 시야 전체에서 인정, 왼쪽 선은 중앙선이 있을 수 있는 위치만 |
| 다른 차가 화면에 보이면 차로를 잘못 잡음 (Gazebo 017: 교차로 뒤 180° 회전) | 차 옆면·바퀴가 검은 선으로 보임 | 한 줄에서 5.5 cm보다 넓은 검은 덩어리와 그 둘레는 차선 후보에서 제외, 막힌 채 제자리 정렬은 25°까지만 |
| 코너에서 마주 오는 차와 접촉 → 맞물려 같이 회전 (Gazebo 018) | 주시거리 30 cm가 코너 전에 미리 꺾어 왼쪽 코너를 16~18 mm 안쪽으로 돎 | 주시거리 21 cm(코너 18 cm), 항상 5 mm 우측, 왼쪽 코너 10 mm 우측, 적분 항은 이 목표 위치 기준 |
| 코너 꼭짓점에서 멈췄다 출발하면 차로를 잃고 FAULT | 지나가는 맞은편 차가 중앙선을 가림, 선이 없으면 직진 | 선을 잠깐 놓치면 직전 곡률 유지, 그래도 없으면 꺾던 쪽으로 제자리 회전(최대 60°) |

## 7. 실차가 생기면 하는 일 (순서대로)

1. **코스 실측**: 가로·세로, 차로 폭, 모서리 반경, 정지선→교차로 거리, 연결로 위치 → `picar_sim/config/course.yaml`. 차 길이·폭도.
2. **차 6대 측정** (3장의 표) → `car0.yaml … car5.yaml`. 회전 흔들림(표준편차)이 3°를 넘는 차는 회전 속도를 낮춰 다시 잰다.
3. **한 대씩 주행**: 차로 이탈·FAULT 없이 두 교차로를 10번씩 통과하는지. 안 되면 그 차의 보정부터 다시.
4. **기록 → SUMO 보정**: 중앙 서버 로그와 스톱워치로 `field_measurements.csv`(속도, 정지 오차, 움직임별 통과 시간) → `picar_sim.calibrate`. 통과 시간 오차 10% 안인지 확인.
5. **가상 실차 범위 갱신**: 잰 값의 범위로 `PRIORS`를 바꾸고 `rehearsal ladder`와 Gazebo `FLEET=` 실행을 다시 → 실차와 시뮬레이션 결과를 나란히 비교.
6. **정책**: 보정된 SUMO에서 기존 정책 평가 → 규칙보다 나쁘면 `--randomize`로 재학습.
7. **실차 운영**: 규칙 제어로 2대 → 6대, DQN은 shadow(판단만 기록) → 저속 active.

## 8. 한계

- 가상 실차의 범위는 가정이다. 실차가 범위 밖이면(예: 모터 차 15%) 결과가 달라진다. `sample_fleet(scale=1.5)`로 넓혀 볼 수 있다.
- 2D 점검기는 차끼리 부딪혀도 밀리지 않는다(그래서 근접 횟수를 따로 센다). 카메라에 다른 차는 이제 보인다. 접촉 뒤의 일은 Gazebo 실행이 본다.
- 2D의 교차로 제자리 회전은 평균 6~7° 덜 돈다(Gazebo는 평균 88°). 2D에서 교차로 출구 스침(`near_junction`)이 Gazebo보다 많이 나오는 이유이고, 2D 모델 쪽을 고쳐야 한다.
- 5.1~5.4의 수치는 다른 차를 카메라에 그리기 전, 주시거리 30 cm일 때 값이다. 지금 코드로는 5분에 도로 구간 근접 0~1회, 교차로 출구 겹침 4~5회(위 항목의 2D 회전 문제 포함, Gazebo 020에서는 0), 교착·FAULT 0이다.
- Gazebo의 가상 실차는 모터·카메라 장착·영상·IR까지 넣었다. 초음파 잡음과 UDP 손실은 2D에만 있다.
- 실행은 차량 묶음 4개 × 시드 2~4개 × 300초다. 실차 운영 시간(수십 분)에 비하면 짧다.
