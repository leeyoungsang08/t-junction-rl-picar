# Sim-to-Real 갭 점검과 보상 설계 재검토 (2026-11-13, 11-15 갱신)

실물 PiCar가 없는 상태에서 쓴 문서다. **이 문서의 "실차 대역" 수치는 실물 측정값이 아니다.** 차마다 하드웨어가 다른 가상 실차 6대를 Gazebo에서 돌린 값이고, 실물을 재면 4장의 빈 칸에 그대로 채워 넣도록 같은 양식으로 썼다.

## 1. 한눈에

| 질문 | 답 |
|---|---|
| 시뮬레이션(SUMO)이 예측한 교통 성능이 실차 대역에서 맞는가 | 보정 전: 통과량 +25%, 지연 -28% 어긋남. 보정 후: 통과량 +5%, 지연 +8% |
| 처음 보는 차 6대에서도 되는가 | 5분 × 8회 중 6회 정상. 실패 2회의 원인(코너에서 차선 놓침, 교차로 출구 접촉)을 고친 뒤 20분 실행 정상 |
| 갭을 가장 많이 줄인 것 | ① 교차로 통과 시간을 움직임별로 재서 SUMO에 반영 ② 차마다 보정 ③ **두 쪽을 같은 정의·같은 시계로 재기** |
| DQN이 규칙보다 나은가 | v9는 아니다(평균 같고 긴 대기가 나쁨). 11-15의 v15는 규칙과 비슷한 수준(평균 3.30 / 3.35 s, 최장 14.3 / 12.8 s)까지 왔고 넘지는 못했다 |
| v9의 긴 대기는 왜 생겼나 | 원인이 둘이었다. ① 정책이 "요청이 얼마나 오래됐는지"를 보지 못했다(관측에 없음) ② 긴 대기 벌점이 20 s부터 시작 |

| 실차 첫 운영 | 규칙 제어(오래된 요청 우선). DQN은 판단만 기록 |

## 2. 보상 설계 5가지 점검

지금 보상(`picar_sim/env.py`, 결정 1회마다):

```
r = − Σ dt × ( 1.0 × 정지선 대기 차량 수 / 전체 차량 수 + 0.5 × (선두 차 대기 − 20 s 초과분)/20 )
    − 0.1 × 신호 전환 횟수 − 50 (교착 시)
```

안전(충돌·허가 없는 진입)은 보상에 없다. 정책이 고를 수 있는 행동을 감독기(supervisor)가 미리 걸러서, 위험한 행동은 선택지에 아예 없다.

### ① 목표를 구체적으로 정의했는가

- **안전 쪽은 했다.** 합격 기준이 숫자로 있다: 충돌 0, 차로 이탈 0, 정지 오차 ±5 cm, 허가 없는 진입 0, 교착 0.
- **성능 쪽은 안 했다.** "지연을 줄인다"까지만 있었고 얼마면 성공인지가 없었다. 그래서 평균이 규칙과 비슷하면 "된다"고 넘어갔다.
- **이번에 정한 것** (교차로 J, 6대, 300 s, 같은 시드로 규칙과 비교):
  평균 지연 ≤ 규칙, p95 지연 ≤ 규칙 × 1.1, 최장 대기 ≤ 15 s, 20초 가드 개입 0회.
  지금 정책(v9)은 첫 항목만 만족한다.

### ② 목표를 작은 단위로 나눴는가

| 원하는 행동 | 보상 항 | 상태 |
|---|---|---|
| 차를 오래 세워 두지 않기 | 대기 차량 비율 | 있음 |
| 한 방향만 굶기지 않기 | 20 s 초과 대기 벌점 | 있으나 **거의 작동 안 함**(⑤) |
| 신호를 쓸데없이 바꾸지 않기 | 전환 비용 0.1 | 있음 |
| 서로 막혀 멈추지 않기 | 교착 −50 | 있음 |
| 빈 방향에 신호 주지 않기 | 없음 | 관찰됨(④), 대기 항으로 간접 처벌 |
| 안전 | 보상 아님, 감독기 | 설계상 분리 |

### ③ 처음부터 다 넣지 않았는가

했다. 실행 기록 이름대로 한 번에 하나씩 바꿨다: v3 순환/직접 선택 → v4 대기 항 → v6 전환 비용 → v7 20초 가드 → v8 요청 나이 관측 → v9 사진 기반 코스 → v10 보정 SUMO + 랜덤화.
다만 v10은 환경(보정된 SUMO)과 랜덤화를 **동시에** 바꿔서, 나빠진 이유를 가르지 못했다. 이번 v11·v12는 그걸 나눠서 했다(⑤).

### ④ 학습 결과를 관찰했는가

부족했다. 평균 지연과 통과량 표만 봤다. 이번에 Gazebo 중앙 서버 기록(6회)과 SUMO(24 시드)에서 행동을 직접 봤다.

| 관찰 | 규칙 | DQN(v9) |
|---|---|---|
| 평균 지연 (보정 SUMO) | 3.35 s | 3.38 s |
| p95 지연 | 10.0 s | 11.9 s |
| 최장 대기 (평균 / 최악) | 12.8 / 17.7 s | **17.3 / 22.7 s** |
| 20초 가드가 강제로 개입 | 0회 | 에피소드당 0.46회 |
| 신호 전환 (Gazebo, 분당) | 5.3~5.8 | 4.7~5.3 |
| 선택지가 둘 이상일 때 규칙과 같은 선택 (Gazebo) | - | 53~64% |
| 차가 없는 방향에 신호를 줌 (Gazebo, 5분당) | 0 | 2~3회 |

"점수는 같은데 행동은 다르다"가 여기서 나왔다. DQN은 신호를 덜 바꾸고 지금 방향을 더 오래 잡는다. 평균은 같지만 누군가는 더 오래 기다리고, 가끔 가드가 대신 끊어 준다.

**정정:** 11-11 문서에 "보정 SUMO에서 v9가 규칙보다 낫다(3.28 / 3.61 s)"고 썼다. 그 수치는 5대·6대, 치우친 교통을 섞은 평균이었다. Gazebo와 같은 조건(6대, 균등)으로 다시 재면 차이가 없다.

### ⑤ 문제 행동의 원인을 찾아 보상을 고쳤는가

- **원인:** 긴 대기 벌점이 20 s부터 시작한다. 그런데 20 s는 감독기가 강제로 끊는 시점과 같다. 8~20 s 구간의 대기는 평균 항에 묻혀서 정책이 신경 쓸 이유가 없다.
- **수정 실험** (시드 1개씩, 1500 에피소드, 보정 SUMO에서 24 시드로 평가):

| 정책 | 바꾼 것 | 평균 지연 | p95 | 최장 대기 | 가드 개입 |
|---|---|---|---|---|---|
| 규칙(오래된 요청 우선) | - | 3.35 | 10.0 | 12.8 | 0 |
| v9 | 기준 | 3.38 | 11.9 | 17.3 | 0.46 |
| v12-s8 | 벌점 시작 20 → 8 s, 가중 0.5 → 1.0 (v9와 같은 환경) | 3.72 | 11.5 | **15.1** | 0.29 |
| v12-s5 | 벌점 시작 5 s | 3.87 | 13.2 | 17.9 | 0.54 |
| v11-s8 | 위와 같되 보정 SUMO에서 학습 | 4.86 | 14.6 | 19.4 | 1.00 |
| v10 | 보정 SUMO + 랜덤화 | 4.34 | 14.3 | 18.6 | 1.38 |

- **읽는 법:** 8 s로 당기면 꼬리가 예상한 방향으로 움직였다(최장 17.3 → 15.1 s, 가드 0.46 → 0.29). 대신 평균이 0.34 s 나빠졌다. 5 s는 너무 일러서 오히려 나빴다. 어느 것도 규칙을 넘지 못했다.
- **보정 SUMO에서 학습하면 나빠진다**(v10, v11). 회전이 느려져 교차로가 오래 막히는 환경에서 같은 1500 에피소드로는 덜 익는 것으로 보인다. 원인은 확인하지 못했다.
- **한계:** 학습 시드가 1개다. 0.3 s 차이는 시드 차이일 수 있다.
- **결론:** 접근로 3개, 차 6대인 이 교차로에서는 "오래 기다린 차부터"가 이미 거의 최선이다. DQN이 이길 여지가 작다. 다음에 고친다면 임계값 대신 요청 나이에 비례해 커지는 벌점을 쓰고, 선택 기준(검증 점수)에 p95를 넣는다.

### ⑥ 11-15 이어서: 원인을 다시 찾고 단계별로 고침

①에서 정한 목표(평균 ≤ 규칙 3.35 s, p95 ≤ 11.0 s, 최장 ≤ 15 s, 가드 개입 0)를 기준으로, 한 번에 하나씩 바꿨다. 학습 시드 2개(42, 43), 보정 SUMO 24 시드 평가.

| 정책 | 바꾼 것 (v9 대비) | 평균 지연 | p95 | 최장 대기 | 가드 개입 | 목표 4개 중 |
|---|---|---|---|---|---|---|
| 규칙 | - | 3.35 | 10.0 | 12.8 | 0 | 기준 |
| v9 (시드 42 / 43 / 44) | - | 3.38 / 3.48 / 3.74 | 11.9 / 11.9 / 12.1 | 17.3 / 16.8 / 16.6 | 0.46 / 0.21 / 0.38 | 0 |
| v13 | 보상: 요청 나이에 비례하는 벌점 추가 | 3.57 / 3.75 | 11.8 / 12.8 | 16.9 / 18.4 | 0.42 / 0.58 | 0 |
| v14 | 관측: 접근로별 요청 나이 추가 | 3.17 / 3.35 | 10.7 / 12.0 | 17.1 / 16.8 | 0.54 / 0.25 | 1~2 |
| **v15** | 관측(v14) + 보상(긴 대기 벌점 20 → 8 s) | **3.30** / 3.72 | 10.9 / 11.3 | **14.3 / 14.7** | 0.04 / 0.08 | 3 / 2 |

- **왜 보상만 고쳐서는 안 됐나(④⑤를 다시 적용):** v9의 관측에는 "정지선에서 기다린 시간"은 있어도 "요청한 지 얼마나 됐는지"가 없었다. 규칙은 바로 그 값으로 순서를 정한다. 볼 수 없는 것을 보상으로 가르칠 수는 없어서 v12, v13은 꼬리가 거의 안 움직였다.
- **관측만 고쳐도 안 됐다:** v14는 평균이 좋아졌지만(3.17 s, DQN이 규칙을 처음 앞섬) 최장 대기는 그대로 17 s다. 보상이 8~20 s 구간을 여전히 안 따지기 때문이다.
- **둘 다 고치면:** v15는 최장 대기 17 → 14.3~14.7 s, 가드 개입 0.2~0.5 → 0.04~0.08회로 두 시드 모두 같은 방향이다. 평균은 시드 42에서 규칙보다 조금 낫고 43에서는 나쁘다.
- **판단:** 규칙과 비슷한 수준이지 더 낫지 않다. 실차 첫 운영은 여전히 규칙이고, 기록만 하는 정책을 v9에서 v15로 바꿀 만하다. v15는 아직 Gazebo에서 행동을 보지 않았다(④).

## 3. 시뮬레이션 네 단계와 갭

| 단계 | 무엇 | 빠르기 | 보는 것 |

### 3.1 교통 성능: SUMO 예측 대 실차 대역 (규칙 제어, 교차로 J, 6대, 300 s)

| | 통과 [대/분] | 평균 지연 [s] | p95 [s] | 최장 [s] |
|---|---|---|---|---|
| SUMO, 보정 전 | 10.15 | 2.24 | 7.6 | 10.3 |
| SUMO, 보정 후 | 8.53 | 3.35 | 10.0 | 12.8 |
| 2D, 가상 실차 6대 | 8.0~8.2 | 2.7~3.5 | - | - |
| **Gazebo, 가상 실차 6대 (실차 대역)** | **8.0~8.2** | **2.6~3.7 (평균 3.09)** | 6.5~8.7 | 11.6~12.1 |
| 갭: 보정 전 → 보정 후 | +25% → **+5%** | -28% → **+8%** | | |

지연은 "요청부터 진입까지 걸린 시간 − 접근 구간을 그냥 달리는 시간(4.98 s)"이다. DQN(v9)은 Gazebo에서 통과 7.8~8.3대/분, 평균 지연 2.5~4.1 s(평균 3.44), 최장 9.3~15.5 s였다.

### 3.2 가짜 갭 하나: 정의와 시계

11-12 보고에 Gazebo 지연을 10~12 s, 통과를 6.2대/분으로 적었다. SUMO의 3.4 s, 8.5대/분과 3배 차이로 보였지만 **측정 방법 차이**였다.

- Gazebo 쪽은 요청→진입 전체 시간을 쟀고, SUMO는 자유 주행 시간 4.98 s를 뺀다.
- Gazebo 쪽은 로그의 벽시계 시간으로 쟀다. PC가 느려 시뮬레이션이 실제의 0.75배속으로 돌았으므로 시간은 1.33배 길게, 분당 대수는 0.75배로 적게 나왔다.

`check_acceptance.py`를 시뮬레이션 시간 기준, SUMO와 같은 정의로 고쳤다. 같은 정의로 재니 3.1의 표처럼 맞는다. "DQN이 Gazebo에서 규칙보다 나쁘다"던 0.4 s 차이도 시드 3개의 흔들림 안이다.

## 4. 실차 검증 절차와 결과표

### 4.1 처음 보는 차에서 드러난 것 (대역 B)

수정에 쓴 차(A)에서는 7회 모두 깨끗했지만, 처음 보는 차(B)에서는 4회 중 1회가 실패했다. 이것이 지금 남아 있는 갭이다.

- **FAULT 1건:** 좌우 모터 차가 가장 큰 차(car1, trim 0.47, 카메라 좌우 3.4° 틀어짐)가 출발 8초 뒤 첫 오른쪽 코너에서 차선을 놓쳤다. 복구 동작은 "꺾던 쪽으로 60° 회전"인데, 놓치기 직전 프레임이 반대쪽으로 꺾고 있어서 왼쪽으로 돌았고 차선을 못 찾았다. 그 차가 길을 막아 전체가 섰다.
  → 복구를 양방향으로 고쳤다(꺾던 쪽 60°, 없으면 반대쪽으로 120°). 재실행(022b) 4회에서 이 실패는 다시 나오지 않았다(4.3).
- **정지 위치:** "가끔 5 cm를 넘는다"고 적었던 것은 **측정 오류였다**(11-15 확인). 넘은 것은 전부 정지선보다 6~9 cm 앞에서 선 경우이고, 모두 0.2 m 앞에 교차로를 건너는 차가 있었다. 장애물 때문에 2~3초 섰다 간 것을 감시 노드가 정지선 정지로 센 것이다. 감시 노드를 고쳤다. 실제 정지선 정지는 A, B 모두 -0.8 ~ +2.2 cm다.
- **교통 성능은 맞는다.** 통과량은 SUMO 예측과 3% 차이다.

안쪽 차로의 오른쪽 코너(반경 0.245 m)는 카메라에 중앙선만 보여서 A에서도 가장 약한 곳이었다. 실차에서도 여기부터 확인해야 한다.

### 4.4 교차로 출구 수정 (11-15)

보상 설계의 다섯 가지를 주행 쪽에도 그대로 썼다.

- **① 목표:** "교차로를 나와 기다리는 차 옆을 지날 때까지, 차체가 차로 중심에서 왼쪽으로 가장 멀리 나간 거리"를 잰다. 목표는 p95 15 mm 이하, 20 mm 초과 1% 이하, 접촉 0.

## 5. 갭을 줄이는 방법 (효과가 컸던 순서)

1. **같은 정의, 같은 시계로 잰다.** 3배로 보이던 지연 차이가 측정 방법 차이였다(3.2). 실차에서도 중앙 서버 로그 하나로 양쪽을 같은 식으로 계산한다.
2. **움직임별 통과 시간을 재서 SUMO에 넣는다.** 보정 전 SUMO는 좌회전을 4.9 s(실제 7.7 s), 우회전을 3.5 s(실제 5.7 s)로 봤다. 이것만으로 통과량 갭이 25% → 5%가 됐다.
3. **차마다 보정한다.** 공용 보정은 1분 안에 전체가 멈춘다. 직진 휨, 속도, 회전, 카메라 장착을 6대 각각 잰다.
4. **단순한 시뮬레이터가 못 보는 것을 지표로 만든다.** 2D는 접촉을 못 보므로 "1.5 cm 이내 근접"을 센다. 다른 차를 카메라에 그린다.
5. **실패 장면을 기록해 되돌려 본다.** Gazebo 카메라 화면을 저장해(`DUMP_FRAMES=1`) 차선 인식에 다시 넣으면 PC 없이 같은 판단이 재현된다. 실차에서도 같은 형식으로 저장하면 된다.
6. **여유를 설계에 둔다.** 코너에서 마주 오는 차 사이는 1.6 cm다. 우측 5 mm 주행, 짧은 주시거리, 차로를 놓쳤을 때의 복구 동작을 넣었다.
7. **랜덤화는 잰 범위로만.** 가정한 범위로 랜덤화한 v10은 오히려 나빴다. 실측 범위가 생긴 뒤에 다시 한다.
